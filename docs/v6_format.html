V6 wire format: changes from V5

V6 changes how quantized FLOAT32 fields are coded inside each 32,768-point chunk. x, y and z are coded as three residual streams against a predictor selected per chunk. Points without a return are excluded by a validity bitmap. Every other FLOAT32 field with a resolution gets one residual stream. The V5 adaptive integer sections are unchanged. Encoders write V6 only when EncodingInfo::version = 6.

1. Motivation: prediction from the previous point

V4 and V5 code each quantized coordinate as a delta from the preceding point in the buffer. How good that prediction is depends on the point order the driver uses.

In firing order, all lasers of one firing are stored, then all lasers of the next firing. The preceding point therefore belongs to a different beam, and the previous return of the same beam is K = number of lasers points back.

In row order, used by organized clouds (height > 1), the preceding point is the adjacent return on the same beam, and K = width reaches the adjacent beam.

buffer order preceding point (V4/V5 reference) point K back (V6 LagK reference)

Ranges in metres, illustrative. Residuals are zig-zag varints of the quantized difference. At 1 mm resolution, 7.47 m is 7,470 steps (2 bytes) and 0.03 m is 30 steps (1 byte). A jump to the 39 m beam is 3 bytes.

Firing order. The LagK or Median predictor references the same beam. Measured effect of the predictor selection: nuScenes +33.1%, Hesai +17.5% (size increase with it disabled).

Row order. The previous-point predictor is already close to optimal. The gain comes mostly from the validity mask and the stream layout. The Median predictor combines the left and upper neighbours.

2. Chunk layout

Both versions split the cloud into chunks of 32,768 points. Stage 1 codes each chunk and stage 2 compresses it with LZ4 or ZSTD.

V5 stage 1 writes the FLOAT32 fields interleaved per point (FloatN varints), then one adaptive section per integer field.

V6 stage 1 writes, in order: the geometry section, one section per other quantized FLOAT32 field, and the V5 integer sections.

q = round(v / resolution). The encoder quantizes in float precision when |q| < 222 and in double precision otherwise. The decoder reconstructs float(double(q) × resolution). An invalid point decodes as NaN or 0.0f on all three axes, and the predictors see the previous value repeated. Each other quantized FLOAT32 field is a section of its own: a u8 mode, then either n raw FLOAT32 values or a residual stream with the Previous predictor.

3. Changes and ablation

Each effect is the increase in ZSTD output size when only that feature is disabled, across the 13 datasets.

Per-chunk predictor

Rationale: the best reference depends on point order and scene.

Selection: the encoder estimates the stage-1 size of each candidate on the first 4,096 points and keeps the smallest. LagK and Median are candidates only when 1 < K and K + 1 < 4,096.

K: the width when height > 1. Otherwise, the lag in [2, 2100] that minimizes Σ|qi − qi−K| over 64 sampled points of the first chunk.

median +2.6%nuScenes +33.1%, Hesai +17.5%

Validity mask

Rationale: no-return points (all three axes NaN, or all three 0.0f) break the prediction twice, once on entry and once on exit.

Coding: the mask kind is the majority kind in the chunk. Invalid points are left out of the streams.

median +4.7%max +10.2% (Ouster OS0-128)

Per-field streams

Rationale: x, y and z residuals have different distributions, and separate streams give stage 2 homogeneous input. Other quantized FLOAT32 fields are coded the same way, one stream each.

V5 +3.2% to +22.4%vs V6 with predictor and mask off

Stage-2 block boundaries

Rationale: ZSTD keeps one set of literal and sequence statistics per block.

Coding: stage 1 passes its section offsets to stage 2, which ends a block (ZSTD_e_flush) at each one. The output is a single standard frame.

median +5.3%range +1.6% to +8.0%

Encoder state cache

Rationale: lag detection and predictor probing need a separate pass over the chunk.

Behaviour: the encoder keeps K, the predictor and the mask kind of each chunk for the next clouds of the stream, whatever their size, and probes again every 16 encodes. x, y, z are quantized with SSE and coded in one pass. On the first encode and on re-probes, only the first 4,096 points (8,192 for lag detection) are quantized for probing. Output bytes are identical either way.

Callers: keep one encoder per stream (PointcloudEncoderCache). A new encoder per cloud always pays the first-encode cost.

The first encode also probes the predictors on a prefix of each chunk: 0.77–1.76× V5, highest on KITTI (1.76×) and the PCD sample (1.74×). Those two datasets have no integer fields, so V5 takes its V4 FloatN path on them, which is the fastest V5 case.

6. Compatibility and validation

Version selection

V6 is written only when EncodingInfo::version = 6. The default is V5. Decoders from 1.3.1 and earlier reject version 6.

Fallbacks

A chunk with an infinite value, or with |q| ≥ 250, is written in raw mode and is bit-exact. The V5 layout is used for version-6 clouds unless x, y, z are the first three FLOAT32 fields with a resolution in (0, 1018); the decoder applies the same test to the header.

Determinism

The float-or-double quantization rule is applied per value. The first (probing) encode and later cached encodes of the same cloud therefore produce identical bytes, which a test checks.

Format freeze and fuzzing

The experiment switches were removed from encoding_config. A mutation test ran 81,000 corrupted V4/V5/V6 messages under ASan and UBSan with no failures. It found signed-overflow bugs, now fixed, and a heap overflow in the V5 RLE decoder, fixed in #149.
